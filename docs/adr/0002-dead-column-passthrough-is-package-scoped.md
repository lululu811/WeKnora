# 死列检测的「整行透传」判定按包算，不按文件算

`dead_columns.go` 判断一个工具是不是「整行透传」（把整份结果集交给模型，读列的是
模型而不是代码）时，判定范围从**文件**改成**包**。

这个判定靠两个正则：找出 `rows, err := ...Query...` 的结果变量，再找出 `: rows`
这种「裸标识符出现在复合字面量的值位置」。原来一个文件就是一个工具，两条都在同一
个文件里，判定成立。

但 spec 包把十一个工具的 SQL 和共用的一段执行器分放在几个文件里 —— SQL 与载荷
不再同文件，按文件判定会把整个 spec 包判成「非透传」，于是那些只被这批工具选中的
指标列会被误报成死列（实测 10 列：`momentum_macd_12_26_9_hist`、`statistics_beta_20`、
`trend_supertrend_*`、`volatility_bbands_20_2_0_*`、`volatility_kc_20_2_*`）。

**为什么按包判定是安全的**：对现有每一个包，按包判定与按文件判定等价。唯一混合的
`query` 包里，非透传的那个文件是生成的目录说明（`sql_query_catalog.go`），它零个
`SELECT`，本来就不产出任何列。

（2026-10-25 补记：那份目录说明后来搬进了 `spec` 包 —— 自由 SQL 工具的声明在那边，
目录是它的说明文字的一部分。`spec` 包本身是透传的那一族，所以这条补记不改变结论。）

**后果**：透传判定从此是包级的 —— 一个包里只要有一个透传工具，整个包的列都被算作
被消费。这是刻意放宽的：它换掉的是「按文件判定漏报」这一类谎（工具明明消费了列，
却被报成死的），代价是「一个包里混了透传工具和挑字段工具」时后者被放过。
